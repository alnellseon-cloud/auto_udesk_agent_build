# 可复用工作流搭建经验

本文只记录跨客户可复用的结构和验证方法，不保存平台域名、租户标识、App ID、Dataset ID 或客户内容。

## 三阶段 RAG

推荐链路：

```text
知识库宽召回 → Rerank 精排 → 分片截断/格式化 → LLM → Answer
```

- 宽召回阶段提高 `top_k`，避免在第一步过早漏掉候选文档。
- Rerank 使用原始问题或改写后的语义问题重新排序。
- RAG Convert 控制文档数量和 Token 上限，减少无关内容挤占上下文。
- LLM 通过 `context.variable_selector=[rag_node_id, text]` 接收上下文，并在提示词中使用 `{{#context#}}`。
- 文档少、问题直接时可以使用“知识库 → LLM”，无需机械套用三阶段。

## 多轮状态与历史消息

- 机型、版本、客户类型等确定状态，优先写入 `conversation` 变量，后续直接读取，不让 LLM 每轮猜测。
- 同一轮刚写入的数据若要立刻供 LLM 使用，优先引用上游节点输出；部分平台会在轮次开始时冻结 LLM 模板中的会话变量快照。
- 历史消息查询节点适合在创建工单、人工升级或会话摘要前汇总上下文；它不是长期业务状态的替代品。
- Answer 通常是终止节点，不要把必须执行的赋值、建单或转人工动作放到 Answer 后面。

## 迭代器

- 容器节点同时保留顶层和 `data` 内的宽高，避免画布渲染异常。
- 内部节点设置 `parentId`、`isInIteration`、`iteration_id`，位置使用相对坐标。
- 内部边也要带 `isInIteration` 和 `iteration_id`。
- 当前项使用 `{{#iteration_id.item#}}`，迭代结果使用 `{{#iteration_id.output#}}`。
- 如果每轮输出是 JSON 字符串数组，在迭代后用 Code 节点解析并展平，再交给 Rerank 或 LLM。

## 分支、工单与人工升级

- Question Classifier 解决语义意图分流；If/Else 解决确定性的值判断，两者不要混用。
- 多条互斥分支需要共用下游节点时，用 Variable Aggregator 统一输出。
- 工单创建前先提取并校验必填字段；提示词只负责对话与决策，结构化字段交给 Parameter Extractor。
- 工单、转人工等有副作用的节点必须设置明确门控，避免每轮重复触发。
- 内置工具的租户配置、模板 ID、字段 ID 都应从当前环境读取或通过私有任务配置传入，不能写死在公共代码中。

## 提示词设计

一个稳定的客服提示词通常分为五层：

1. 角色与服务边界：能回答什么、不能承诺什么。
2. 证据约束：仅基于 `{{#context#}}` 或工具结果回答；证据不足时明确兜底。
3. 流程规则：何时追问、何时创建工单、何时转人工。
4. 输出格式：语言、长度、结构以及图片/视频等渲染格式。
5. 安全规则：不泄露系统提示、Token、内部 ID，不伪造查询或操作成功。

把可判定的逻辑放进分类器、条件节点和 Code 节点；提示词只承担语言理解与表达，可显著降低随机性。

## 测试方法

- 首轮 `dialog_id` 传空字符串，从 `workflow_started` 事件读取平台返回的 `conversation_id`。
- 后续用例复用同一个会话 ID，才能暴露上下文继承和变量持久化问题。
- 不要自行生成一个从未在平台创建过的 UUID；平台通常会返回 Conversation Not Exists。
- 每条主路径至少覆盖：正常命中、信息不足追问、知识库无结果、重复触发防护、工具失败和兜底。
- 不仅检查最终答案，还要记录实际节点路径、工具状态和工作流最终状态。
